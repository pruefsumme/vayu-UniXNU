# SM8150 (Snapdragon 855/860) XNU/iOS ports: page size and what a Poco X3 Pro (vayu) port reuses

Research date 2026-11-24. All repo facts below come from shallow clones / `gh api` reads of public repos (nothing executed). Repo state is as of the clone date; these projects move daily.

## 1. Does Kryo 485 / Cortex-A76 / A55 support a 16 KiB translation granule (TGran16), so stock 16K XNU can run?

### Takeaway
Yes. Both Cortex-A76 and Cortex-A55 report ID_AA64MMFR0_EL1.TGran16 = 1 (16K supported), and 16K XNU has been booted on real SM8150 hardware (Pixel 4, Mi 9 derivatives, and a vayu bring-up) and on the sibling SM7150 (Kryo 470). No 4 KiB patching is needed for the CPU. The one authoritative Arm TRM page could not be fetched (JS-rendered), so the hard evidence is the QEMU model values plus on-hardware reads by ios-sweet. The 4K problem only appears on Cortex-A53 class cores (ios-topaz).

### Cited Findings
- QEMU's `cortex-a55` and `cortex-a76` CPU models both set `ID_AA64MMFR0 = 0x0000000000101122`. Decoded: TGran16 (bits 23:20) = 1 (16K supported), TGran4 (31:28) = 0 (4K supported), TGran64 (27:24) = 0 (64K supported), PARange = 2 (40-bit PA), ASIDBits = 2 (16-bit). QEMU takes these values from the cores' documented/real ID registers; this is secondary evidence, not the Arm TRM itself. — [QEMU target/arm/tcg/cpu64.c](https://github.com/qemu/qemu/blob/master/target/arm/tcg/cpu64.c) (fetched raw; `aarch64_a55_initfn` and `aarch64_a76_initfn`)
- Linux encodes the field: TGRAN16 shift 20, 0x0 = not implemented, 0x1 = supported (0x2 = 16K with LPA2). — [Linux arm64 cpu-feature-registers doc](https://docs.kernel.org/arch/arm64/cpu-feature-registers.html); [Linux patch discussion on TGRAN ranges](https://lists.infradead.org/pipermail/linux-arm-kernel/2021-March/643036.html)
- On-hardware read on a Redmi Note 10 Pro (SM7150, Kryo 470 = A76/A55-derived): "Entry EL1, MMU off ... ID_AA64MMFR0 = ...101122: 16K granule YES, 4K YES", and "Milestone 3: 16K MMU verified" with a working 16K-granule TCR (TCR 0x1409CB51C, PARange 2). — [ios-sweet docs/ios-sweet/NOTES.md in ios-flame mirror](https://github.com/NWylynko/ios-flame/blob/main/docs/ios-sweet/NOTES.md) (also in the dipa-studio/ios-sweet repo)
- ios-sweet README: CPU "6 of the 8 cores (the six Cortex-A55s) via PSCI, 16K pages"; the two A76 cores were unused in ios-sweet. — [ios-sweet README](https://github.com/dipa-studio/ios-sweet)
- ios-flame (SM8150, Pixel 4) runs "All 8 cores (4x Cortex-A55 + 4x Cortex-A76) at full clock" with the stock-16K SWEET machine config; the SWEET config is built on the BCM2837 template with `#define __ARM_16K_PG__ 1` (patch 0004) and the shim's MMU code is "the 16K granule XNU uses". Its notes say "SWEET uses 16K pages" and the GPU is mapped in 4K steps from 16K VM pages. — [ios-flame README](https://github.com/NWylynko/ios-flame), [patch 0004](https://github.com/NWylynko/ios-flame/blob/main/xnu/patches/0004-sweet-machine-config.patch), [shim/mmu.c](https://github.com/NWylynko/ios-flame/blob/main/shim/mmu.c), [patch 0115](https://github.com/NWylynko/ios-flame/blob/main/xnu/patches/0115-flame-gpu-v2-client-turnip.patch)
- Flame's live-FDT hardware facts: CPU 4x A55 + 3x A76 + 1x A76 prime, MIDR 0x51df805e, GIC-600, timer 19.2 MHz, PSCI 1.1 via smc. — [ios-flame NOTES.md](https://github.com/NWylynko/ios-flame/blob/main/NOTES.md)
- Counter-example proving the check matters: ios-topaz (Redmi Note 12 4G, SM6225) found that its ABL starts on a Kryo 260 Silver core (Cortex-A53 class, MIDR 0x51AF8014) "which has no 16K translation granule (ID_AA64MMFR0.TGran16 = 0)". Fix: shim wakes the Gold (A73-class) core 0x100 via PSCI CPU_ON, parks the Silver core, and XNU runs on Gold only (the Gold cluster has TGran16). Its optional "all 8 cores" path is patch 0140, `TOPAZ_4K=1`, which builds SWEET with 4 KiB pages. — [ios-topaz README](https://github.com/MakrSas/ios-topaz), [shim.c](https://github.com/MakrSas/ios-topaz/blob/main/shim/shim.c), [patch 0140](https://github.com/MakrSas/ios-topaz/blob/main/xnu/patches/0140-topaz-4k-pages.patch)
- Android's official 16 KB page docs state only that "ARM CPUs support the larger 16 KB page size" and give no SoC list; no SoC-specific support list exists there. — [Android 16 KB page size](https://source.android.com/docs/core/architecture/16kb-page-size/16kb)
- HakiOS fork for vayu (Snapdragon 860 = SM8150-AC, 4x A55 + 4x A76) boots XNU on this SoC with a loader that assumes 16K pages (`BASE_ALIGN` "32 MB: L2 block size with 16K pages", `PAGE_SIZE_MAX 0x4000`) and the kernel built from the BCM2837 config; the README claims boots "to launchd" and "SpringBoard on screen" on vayu hardware. — [telegdyd/ios-vayu devices/poco-x3-pro/README.md](https://github.com/telegdyd/ios-vayu/blob/vayu-dev/devices/poco-x3-pro/README.md), [xnuloader/loader.c](https://github.com/telegdyd/ios-vayu/blob/vayu-dev/xnuloader/loader.c)
- Early vayu attempt PowerPointKotik/ios-vayu ran the unmodified ios-sweet SWEET (16K) kernel with a vayu ADT: it changes DRAM window (`dram-base 0xc0000000`, 3 GiB), framebuffer `0x9c000000+0x2400000`, adds `xiaomi,vayu`/`qcom,sm8150` to root compatible, keeps `qcom,kryo470` CPU strings "vayu's Kryo 485 has the same MPIDR Aff1:Aff0 layout". Its doc is a bring-up log (stack overflow in a touch probe fixed 2026-10-22); it does not claim a home screen on vayu. — [VAYU.md](https://github.com/PowerPointKotik/ios-vayu/blob/main/VAYU.md)

### Inferences
- Kryo 485 is an A76/A55 derivative core pair, as is Kryo 470; ios-sweet's on-hardware 0x...101122 read on Kryo 470 plus QEMU's A55/A76 values plus ios-flame booting 16K XNU on all 8 SM8150 cores makes TGran16 = 1 on vayu's Kryo 485 near-certain. Nobody I found has printed the vayu register itself.
- A vayu port does not need UniXNU's 4K XNU patches for the CPU; the 4K path in UniXNU exists because most of its targets use a non-16K-safe start-up core, a generic default, or SMMU/userland-ABI convenience, not because of A76/A55.
- Boot-core caveat: ios-topaz shows ABL may start on a core different from the one you expect; for SM8150 ios-flame does not report such a handoff (it boots on the stock ABL core), and HakiOS vayu uses `bootcpu=7` (a prime A76), so check the boot CPU's MIDR on vayu's ABL/UEFI path.

### Gaps
- Arm's own Cortex-A76 TRM (DDI/100798) and Cortex-A55 TRM (100442) ID_AA64MMFR0_EL1 pages redirect to a JS-rendered site that returned no content via fetch; no first-party Arm quote obtained. Value taken from QEMU model plus Linux field definition.
- No Android/Qualcomm document listing "SoCs that support 16K" was found.
- No measured ID_AA64MMFR0_EL1 dump from an actual Snapdragon 855/860 device found in the repos (flame shim logs it at boot, `shim/shim.c:159`, but the value is not in the published notes).

## 2. What ios-flame (Pixel 4, SM8150) and ios-sweet did

### Takeaway
ios-sweet (Redmi Note 10 Pro, SM7150) is the base: stock XNU xnu-8796 (iOS 16 generation) with 81 patches, a custom bare-metal "shim" that acts as iBoot and a synthetic Apple Device Tree, booted by `fastboot boot` from the unlocked Android bootloader, running the unmodified iPhone X iOS 16.7.16 userland from an HFS+ image in `userdata`. ios-flame adds patches 0082-0124 and reaches Metal-rendered SpringBoard/Safari on the Adreno 640, Wi-Fi, touch, USB Ethernet. Page size is 16K throughout (no 4K work).

### Cited Findings
**Page size / kernel config**
- Machine config: SWEET, derived from BCM2837 (generic ARM, no Apple sysregs) + VMAPPLE-style GICv3, with `__ARM_16K_PG__ 1`; plain arm64 not arm64e (Kryo has no PAC); Group 1 IRQ path for the GIC timer (PPI/INTID 19) because NS EL1 cannot use Group 0 FIQ; PSCI via `smc` not `hvc`. — [ios-sweet NOTES.md (XNU loader design / Kernel architecture plan)](https://github.com/NWylynko/ios-flame/blob/main/docs/ios-sweet/NOTES.md), [patch 0004](https://github.com/NWylynko/ios-flame/blob/main/xnu/patches/0004-sweet-machine-config.patch)
- Boot CPU/PE facts: PSCI 1.1, CPU_ON works for all 7 secondaries (MPIDR 0x81000n00). — [ios-flame NOTES.md](https://github.com/NWylynko/ios-flame/blob/main/NOTES.md)

**Device tree**
- Apple Device Tree is built by `tools/mkadt.py`: it starts from a real iPhone X (D22AP) device tree from the IPSW (the earlier note says an iPhone 8 d20ap template) for the `/product` and identity nodes, and fills `/chosen`, `memory-map`, cpu/GIC/timer/UFS/fb nodes with flame values from the live Android FDT. Compatible strings and node names stay "Redmi"/sweet names (`xiaomi,sweet`, `qcom,kryo470`, `sweet,display`) because built-in drivers match them. RAM base is placed above XNU-unsafe Qualcomm XPU carve-outs (`--highmem` = 0x1_00000000, size 0xfcc00000). — [tools/mkadt.py](https://github.com/NWylynko/ios-flame/blob/main/tools/mkadt.py), [NOTES.md](https://github.com/NWylynko/ios-flame/blob/main/NOTES.md)

**Kernel/userland/firmware sources**
- Kernel: Apple open-source XNU xnu-8796.141.3, patches 0001-0081 from ios-sweet + 0082-0124 for flame, built with blacktop/darwin-xnu-build and (per ios-sweet) an older Xcode because Xcode 16 `iig` needs a patch (0082 IORPC.kernelContent). — [ios-flame README](https://github.com/NWylynko/ios-flame), [CREDITS.md](https://github.com/NWylynko/ios-flame/blob/main/CREDITS.md)
- Userland: iPhone X iOS 16.7.16 (20H392) IPSW fetched piecewise via `tools/remotezip.py`, converted to an HFS+ image with `tools/mkiosroot.sh` (apfs-fuse, hfsprogs, in a Linux VM) and `tools/sweet-root-tweaks.py`; written to `userdata` (sda15) from TWRP with `dd` (not `fastboot flash`: "ABL hangs on the last chunk"). None of Apple's/Google's/Qualcomm files are in git. — [ios-flame README ("Not in git")](https://github.com/NWylynko/ios-flame)
- Firmware: taken from the factory image's `vendor.img` `/firmware`: GPU `a640_gmu.bin`, `a640_zap.mdt/.b02`, `a630_sqe.fw`; Wi-Fi `wlanmdsp.mbn`, `modemuw.jsn`, `bdwlan-flame.bin`, modem `modem.mdt/.bNN`; plus the user's own modemst1/2/fsg/fsc backups for rmtfs. — [ios-flame README](https://github.com/NWylynko/ios-flame)

**Boot method and unlock**
- `fastboot boot shim-boot.img` from Google's unlocked ABL; nothing flashed to the boot chain; every reset returns to fastboot because the shim sets the PM8150 PON reason. ABL rules found the hard way: kernel must be LZ4-frame compressed, Image header text_offset 0x80000, AVB hash footer (algorithm NONE, padded to 64 MiB), boot header v2 with stock SM8150 dtb; ABL loads kernel at 0x80080000, DTB at 0x84500000, ramdisk at 0x84700000. Test loop: TWRP in `boot_a` to read logs. — [ios-flame NOTES.md](https://github.com/NWylynko/ios-flame/blob/main/NOTES.md)
- Unlock requirement: bootloader unlocked via `fastboot flashing unlock`, which wipes the phone; OEM unlocking enabled in developer options; phone on final Android 13 build TP1A.221005.002.B2. Data is erased (iOS root lives in userdata). — [DEVICE.md](https://github.com/NWylynko/ios-flame/blob/main/DEVICE.md), [README](https://github.com/NWylynko/ios-flame)

**SoC-generic vs Pixel-4-specific** (from the patch list in NOTES.md and README credits)
- Largely SoC-generic (cepheus fork says: "GIC, timer, PSCI, PMIC, USB, UFS, GPU registers, SDE display engine copy directly"): GIC-600 / timer / PSCI, PM8150 PMIC/RTC/reboot reason, RPMh votes (0102, 0120, 0122), DWC3 USB + Ethernet-over-USB + file server (0088-0093), UFSHCI 3.0 @0x1d84000, /dev/pmem (0094), A640 GPU core + GMU/ZAP + present path (0095, 0105-0122), SweetAccelerator and the v2 NativeAdreno-ABI client for Turnip (0096-0097, 0115-0116), WCN3990 Wi-Fi via userland `wland` (0123, from ios-topaz/HackiOS).
- Pixel-4-specific: NT37280 1080x2280 command-mode DSC panel left running by ABL, ABL autorefresh on INTF1 (0083/0084/0110-0112 continuous corners), ST FTS (ftm5) touch over GENI SPI (0085-0086), PM8150 GPIO6 for vol+ , Google ABL boot image rules, flame bdwlan board data, partition layout. The Redmi sweet patches (Goodix touch, video-mode panel, PM6150L) are replaced/disabled on flame. — [ios-flame NOTES.md](https://github.com/NWylynko/ios-flame/blob/main/NOTES.md), [ios-cepheus README](https://github.com/Mattia990/ios-cepheus)

**Status / limits (2026-10-22, kernel 0124)**
- Works: all 8 cores, UFS 3.0, 1080x2280 display (scaled to iPhone X 1125x2436 by the A640), Metal via metal2vulkan + Mesa Turnip (about 20-26 fps swiping), touch, buttons, USB networking/SSH, Wi-Fi (Settings works), Settings/Safari/Clock/Calendar/Notes/Photos, ad hoc-signed third-party IPA.
- Not working: audio, video playback, Bluetooth, cellular, camera, sensors, GPS, SEP/Face ID, HEIC/HEVC decode, real battery readings. Security mostly off (permissive AMFI/sandbox, stub keystore); erases Android userdata; "Experimental bring-up, not a usable phone OS."
- Roadmap: no formal roadmap file; `METAL-NEXT.md` describes the plan for user-quality Metal (metal2vulkan + Turnip); HANDOFF.md lists open items (Wi-Fi join from Settings, radio restart, etc.). The NWylynko/ios-flame repo has issues disabled. — [README](https://github.com/NWylynko/ios-flame), [METAL-NEXT.md](https://github.com/NWylynko/ios-flame/blob/main/METAL-NEXT.md), [HANDOFF.md](https://github.com/NWylynko/ios-flame/blob/main/HANDOFF.md)
- ios-flame has a single squashed commit ("Docs for flame: README, notes, engineering log, recovery, credits", 2026-10-22). ios-sweet was last pushed 2026-10-23, 1386 stars; open issues include #10 "GPU support", #14 "SM8350 (star / Mi 11 Ultra): undefined-instruction panic right after GIC init". — [ios-sweet GitHub](https://github.com/dipa-studio/ios-sweet)
- ios-flame has forks for other SM8150 devices already: ios-cepheus (Mi 9; "most low-level bring-up code copies directly from ios-flame"), ios-hotdogb, ios-guacamole, plus the vayu forks below. — [forks list](https://github.com/NWylynko/ios-flame/forks) (via `gh api repos/NWylynko/ios-flame/forks`)

### Inferences
- A vayu port is the same recipe as the cepheus fork: copy flame's SoC-generic patches; replace panel, touch, GPIO, memory layout, partition offsets, board firmware blobs. The Poco X3 Pro (SM8150-AC, Snapdragon 860) differs from the 855 mostly in clocks/bins, so SoC-generic code should apply, but this is not documented anywhere I found.
- The boot path depends on the device's ABL accepting `fastboot boot` with an unsigned/AVB-footered image while unlocked; Xiaomi's ABL rules for vayu are not documented in flame and need testing (ios-topaz had to adapt to Xiaomi ABL ignoring boot v1/v2).
- Page size is a non-issue for the flame/sweet route: it is the unmodified stock 16K config.

### Gaps
- Exact content of each Pixel-4-specific patch (only one line per patch in NOTES.md was read, not the diffs).
- Xiaomi bootloader unlock requirements for vayu (Mi Unlock account/waiting period) not researched here; outside the sources listed.
- ios-flame's sibling kernel numbering "0140 4K pages" referenced in HANDOFF is ios-topaz's patch, not flame's.

## 3. UniXNU catalog: SM8150 devices, Port-a-device guide, SoC support, Adreno 640 / Turnip

### Takeaway
UniXNU (shallow clone at commit `8542980`, 2026-11-19) lists 29 SM8150 device records (plus SM8250-AC, SM7150 sweet) but no vayu, no davinci, no Pixel 4/flame/coral. Redmi K20 Pro / Mi 9T Pro (raphael), Mi 9 (cepheus), Mi Mix 3 5G (andromeda) and Xiaomi Pad 5 (nabu) are the Xiaomi SM8150 entries. UniXNU's own GPU path is A740-only (Adreno740 + AdrenoMetal + Turnip Darwin KMD); no A640 component exists, though Turnip itself is the Mesa a6xx/a7xx Vulkan driver. UniXNU itself builds 4K XNU (BCM2837 config with 12-bit granule patches), a different design from ios-sweet's 16K.

### Cited Findings
**UniXNU basics**
- UniXNU is "a general UEFI environment and driver loading system, similar to OpenCore": BootShim + Mu-Silicium UEFI firmware (via `fastboot boot`) -> UniXNU boot manager -> DarwinBoot -> patched XNU -> IPSW userland. Device repos are community-maintained; only sheng (SM8550 Xiaomi Pad 6S Pro) is "officially maintained". — [UniXNU docs/porting/index.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/index.md), [docs/devices/index.md](https://github.com/UniXNU/UniXNU/blob/main/docs/devices/index.md)
- Page size: "Apple ARM64 kernels use a 16 KiB page on most SoCs. Non-Apple ARM64 SoCs commonly use a 4 KiB granule. UniXNU builds XNU for the BCM2837 machine configuration, which carries the 4 KiB layout, and patches the places where XNU assumes 16 KiB." Patches include `native-4k-bootstrap-capacity`, `native-4k-user-abi` (64-bit user processes get 4K, commpage and shared-region 4K), `native-4k-signature-hash-cache` (derives 4K page hashes from the kernelcache's 16K CodeDirectory, build flag `XNU_NATIVE_CS_HASH_CACHE`), `pgz-aligned-validation`, `zzx-pmap-sync-64bit-pa` (DRAM above 4 GiB), `apple-only-cpu-tunables`, `non-apple-cache-monitor`. `ArmSmmu4K` is the SMMU driver. — [docs/xnu/four-k-page-tables.md](https://github.com/UniXNU/UniXNU/blob/main/docs/xnu/four-k-page-tables.md), [docs/drivers/arm-smmu4k.md](https://github.com/UniXNU/UniXNU/blob/main/docs/drivers/arm-smmu4k.md)
- The same page documents that an Apple 4K profile switches to 16K above 1 GiB RAM and native 4K stays 4K at any RAM. — same page.

**SM8150 records in devices.toml** (python tomllib parse, 410 device records; SoC counts: SM8550 97, SM8250 47, SM8150 29, ...) — [devices.toml](https://github.com/UniXNU/UniXNU/blob/main/devices.toml)
- SM8150 names (soc = "SM8150"): alphaplus (LG G8 ThinQ), andromeda + andromeda-giannoccarol (Xiaomi Mi Mix 3 5G), cepheus + 3 variants (Xiaomi Mi 9), d2xq (Galaxy Note10+ 5G), flashlm (LG V50), guacamole (OnePlus 7 Pro), hotdog (OnePlus 7T Pro), mh2lm (LG G8X), nabu + 8 variants (Xiaomi Pad 5), pclm10 (OPPO Reno Ace), pd1936 (iQOO Neo 855), raphael + 6 variants (Redmi K20 Pro / Mi 9T Pro). SM7150: sweet (Redmi Note 10 Pro, 2 records).
- **No vayu, davinci, flame, coral, Pixel 4 or Poco record**; `grep -riE 'vayu|poco x3|davinci'` over the whole repo returns nothing; "flame/coral/pixel 4" also absent.
- Statuses (summary field): cepheus "Device repository and boot chain prepared; no hardware result"; guacamole "iOS 16.7.16 userland reached; GPU pending"; nabu "launchd exec returns ENOENT; Linux kernel builds"; raphael "Public source access pending; current build and device state unconfirmed". Raphael variants (Aruvelut-123: iPadOS 18.7.12 arm64; Gsjsjzhznsz, guowenye: "compile-only default with separately gated native handset bring-up") have `record_state = available`; components for these are only XnuPrelink, DarwinBoot, ArmDTPlatform. d2xq and pd1936 records are `invalid`.
- OnePlus 7 Pro guacamole (SM8150, closest precedent): "The kernel and root file system come from the ios-sweet guacamole work; UniXNU and DarwinBoot provide the boot chain", using Project Aloha (SurfaceDuo1Pkg `SM8150_EFI.fd`) UEFI, bootimg via `fastboot boot`, r15 reaches iOS userland; "GPU and GMU: blocked in the ios-sweet tree". This is UniXNU's pattern for SM8150: the sweet/flame 16K kernel plus UniXNU boot chain. — [docs/devices/guacamole.md](https://github.com/UniXNU/UniXNU/blob/main/docs/devices/guacamole.md)

**Port a device guide and effort**
- Eight steps: (1) collect inputs, (2) choose shared support, (3) create the device repository (copy `examples/device`, fill `board.toml`, `feeds.toml`, DTS, `proprietary-files.txt`, `porting.toml`), (4) resolve/inspect the build (`./unixnu defconfig/fetch/status/tree`), (5) hardware description (DTS -> ADT) and firmware (UEFI integration), then the later steps (driver adaptation, build images, boot/verify). A new SoC needs a `UniXNU-<soc>-common` repo with `soc.toml`, `dts/<soc>.dtsi`, `configs/<soc>.config`, `patches/xnu/series`, `kits/`. — [docs/porting/steps.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/steps.md), [docs/porting/soc-support.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/soc-support.md)
- I found **no effort estimate** (hours/days/weeks) anywhere in UniXNU's docs (grep for effort/estimate/difficulty/weeks/months over docs/porting, docs/guide, README returned nothing relevant). The docs are procedural, with "Result:" statements per step.
- There is no SM8150 SoC repo documented in the SoC support page; the only implemented SoC repo named is SM8550 (`UniXNU-sm8550-common`). A "SoC support page for SM8150" does not exist in the docs (the SM8150 SoC repos for guacamole etc. live in community device repos).

**GPU (Adreno 640 / Turnip)**
- The GPU guide path is "Metal -> AdrenoMetal -> metal2vulkan -> Turnip -> Darwin KMD -> Adreno740 -> A740". "For another GPU generation, implement the matching kernel backend and compiler support before selecting its frontend." The component catalog's Adreno components are only Adreno740, AdrenoMetal, AdrenoPM4 (A740 command layouts), AdrenoFirmware (A6xx/A7xx HFI). Device records reference "Adreno650" (alioth, SM8250) and "Adreno 610" (tb128fu, summary "Metal frames presented by the GPU; Adreno 610 runs") as community work. There is no Adreno 640 component or doc page. — [docs/porting/gpu.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/gpu.md), [components.toml](https://github.com/UniXNU/UniXNU/blob/main/components.toml)
- UniXNU does carry Turnip/Mesa patches (`patches/mesa/turnip-darwin-kmd.patch` adding `tu_knl_darwin.cc`, `turnip-gmem-mutable-swap.patch`, `turnip-builtin-shader-pack.patch`) and `AdrenoMetal` (NativeMetal, NativeAdreno ABI). Turnip is Mesa's freedreno Vulkan driver, so an a6xx path exists upstream; the Darwin KMD (`tu_knl_darwin`) is generic across generations but UniXNU's kernel-side driver (Adreno740) is A7xx. ios-flame reuses UniXNU's `NativeAdrenoABI.h` and Mesa patches with its own A640 kernel driver (flame patches 0095, 0115). — [UniXNU patches/mesa/](https://github.com/UniXNU/UniXNU/tree/main/patches/mesa), [ios-flame CREDITS.md](https://github.com/NWylynko/ios-flame/blob/main/CREDITS.md)
- HakiOS vayu records a working Adreno 640 path: "3D | Adreno 640 | `vayu_adreno.c`, with `hakios.gpu.cpp` and Mesa/freedreno in user space | hardware: SpringBoard drawn on the GPU", needing the GPU firmware and signed zap shader from the user's own phone; also a `docs/vayu-patches/0040-hakios-metal-a640-gen2-port.patch` (hakios-metal A640 port). — [telegdyd/ios-vayu devices/poco-x3-pro/README.md](https://github.com/telegdyd/ios-vayu/blob/vayu-dev/devices/poco-x3-pro/README.md)

### Inferences
- Reusing UniXNU for vayu would mean a 4K XNU kernel built from UniXNU's profile, new `vayu` device repo plus an SM8150 SoC repo (no maintained SM8150 common repo documented), the Mu-Silicium `vayuPkg` UEFI (HakiOS confirms `vayuPkg` and `Resources/DTBs/vayu.dtb` exist in Mu-Silicium) and the Adreno 640 kernel driver which UniXNU does not provide. UniXNU's own SM8150 pattern (guacamole) is actually "ios-sweet 16K kernel + UniXNU boot chain", i.e. the 16K route.
- Since 16K XNU is supported by the hardware, UniXNU's 4K patches are optional for vayu; the practical reuse is its boot chain (Mu-Silicium UEFI + DarwinBoot), Metal frontend (NativeMetal, metal2vulkan) and Turnip Darwin KMD patches, not its page-size work.
