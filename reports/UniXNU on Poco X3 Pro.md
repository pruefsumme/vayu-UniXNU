# Sibling Ports, Not UniXNU, Can Reach Vayu

UniXNU does not support the Poco X3 Pro (vayu) today, and it is not the shortest route to getting iOS userland running on it. The project is a UEFI-based loader plus a 4 KiB-page XNU build, and its only first-party port is the Xiaomi Pad 6S Pro (sheng, SM8550); its device catalog has about 410 records and none is vayu. The same SoC family already has a different lineage of ports: ios-flame (Pixel 4, SM8150) reportedly reaches Metal-rendered SpringBoard with Wi-Fi on a 16 KiB-page kernel, and at least four public repos target vayu itself, one of which (`telegdyd/ios-vayu`) claims touch, GPU, Wi-Fi, audio and camera results that its own author flags as untested since a rebuild. The realistic ceiling on your unit is an experimental iPhone X-identity iOS 16.7.x bring-up: boot from RAM via `fastboot boot`, SpringBoard, touch, a UFS root, USB networking, probably Wi-Fi and slow GPU compositing, and no cellular, Bluetooth, camera, sleep or Apple services. Every performance and status claim in this report is self-published between October and November 2026, with no independent reproduction found, so "verified" below means "seen published in a repo, doc or device tree", never "seen running". The phone is currently locked, so the gating item is Xiaomi's unlock approval, which sources put anywhere from 72 hours to more than 7 days and which wipes the device. Device context for all of this: Poco X3 Pro (vayu), SM8150-AC, global M2102J20SG, 8 GB RAM, Android 13/MIUI 14, bootloader locked, OEM-unlock toggle allowed, non-A/B layout.

## UniXNU boots Apple's kernel through an OpenCore-style UEFI layer

UniXNU's README calls it an independent project that works "like OpenCore": a general UEFI environment and driver-loading system that loads the drivers a device needs and boots the OS through a common UEFI layer ([README](https://github.com/UniXNU/UniXNU/blob/main/README.md)). The boot chain, as documented, runs from the Android bootloader into a boot image whose kernel field holds a BootShim plus a UEFI firmware volume, then into `UniXNU.efi` (which reads `\EFI\UniXNU\unixnu.toml`, loads driver entries, patches the device tree and builds a menu), then into `DarwinBoot`, which validates the kernel, builds an Apple-style device tree and boot arguments, exits boot services and jumps to XNU at EL1 ([boot-chain.md](https://github.com/UniXNU/UniXNU/blob/main/docs/concepts/boot-chain.md)). The firmware layer is a Mu-Silicium fork (`uefi-sheng`), and the image is launched from RAM with `fastboot boot` rather than flashed ([uefi-sheng](https://github.com/UniXNU/uefi-sheng), [sheng.md](https://github.com/UniXNU/UniXNU/blob/main/docs/devices/sheng.md)). XNU itself is Apple's public source plus about 60 patches, with profiles for xnu-10063 (iPadOS 17.7.11, arm64) and xnu-12377 (iPadOS 27.0.1 arm64e, macOS 27.3) ([source-and-patches.md](https://github.com/UniXNU/UniXNU/blob/main/docs/xnu/source-and-patches.md), [devices.toml](https://github.com/UniXNU/UniXNU/blob/main/devices.toml)).

The distinctive design choice is page size. Apple kernels use 16 KiB pages, while non-Apple ARM64 SoCs commonly use a 4 KiB granule, so UniXNU builds XNU for the generic `BCM2837` machine configuration and patches the places that assume 16 KiB: bootstrap page tables, the user ABI, and code-signature hashing (the 16 KiB CodeDirectory hash is checked, then split into per-4 KiB hashes) ([four-k-page-tables.md](https://github.com/UniXNU/UniXNU/blob/main/docs/xnu/four-k-page-tables.md), [security.md](https://github.com/UniXNU/UniXNU/blob/main/docs/concepts/security.md)). Using the BCM2837 config also means no Apple-only features (PPL, SPTM, KTRR) are needed; the non-SPTM pmap is used, which I read as the reason generic cores can run the kernel at all. The CPU baseline is GICv3, the ARM generic timer and PSCI ([arm-cpu.md](https://github.com/UniXNU/UniXNU/blob/main/docs/drivers/arm-cpu.md)). On the GPU side, the documented path is Metal, AdrenoMetal, metal2vulkan, Mesa Turnip, a Darwin kernel-mode driver and the native `Adreno740` XNU driver, with AirNir compiling Apple AIR to NIR ([adreno740.md](https://github.com/UniXNU/UniXNU/blob/main/docs/drivers/adreno740.md)). Security is largely Apple's own stack run against a boot-supplied trust cache, plus a signed-policy root layer and an AppSync-style path so unsigned IPAs install; there is no FairPlay or App Store authorization ([security.md](https://github.com/UniXNU/UniXNU/blob/main/docs/concepts/security.md)).

PAC is the hard split in what a given SoC can run. The arm64e iPadOS 27 profile requires FEAT_PAuth on every core with writable EL1 key registers, and only sheng is listed as arm64e-capable (in development); non-PAC chips stay on arm64 profiles with iOS 16 or iPadOS 17 ([arm64e.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/arm64e.md)). Kryo 485 is an Armv8.2-class A76/A55 design without pointer authentication. That is background knowledge in the notes, backed by ios-sweet describing its sibling SM7150 as "ARMv8.2 without pointer authentication" ([ios-sweet README](https://github.com/dipa-studio/ios-sweet)), so vayu cannot take the iPadOS 27 profile.

## Only one tablet is first-party; vayu's siblings are mostly unfinished records

UniXNU's own docs state that device repositories are community-maintained and only sheng is officially maintained ([porting/index.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/index.md), [devices/index.md](https://github.com/UniXNU/UniXNU/blob/main/docs/devices/index.md)). The sheng record shows iPadOS 27 reaching the Home Screen with Settings opening and a native Adreno 740 Metal device in use, plus a macOS 27.3 capture that reached the desktop; Bluetooth, USB and keyboard are marked `device-verified` while display, GPU, network and audio are only `implemented` (source exists, no device proof), and the same page says the macOS 27.3 argument set was "not yet run on hardware" in another passage ([sheng.md](https://github.com/UniXNU/UniXNU/blob/main/docs/devices/sheng.md), [records.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/records.md)). Known limits include no suspend, fixed backlight, no accelerometer, low-battery panics and fairplayd/adid disabled so SpringBoard can finish starting.

The catalog is much larger than the working set. devices.toml has 410 records (SM8550 97, SM8250 47, SM8150 29), many with states like "kernel and image integration pending" or `record_state = "invalid"` ([devices.toml](https://github.com/UniXNU/UniXNU/blob/main/devices.toml)). Its SM8150 entries include Xiaomi Mi 9 (cepheus: "no hardware result"), Xiaomi Pad 5 (nabu: "launchd exec returns ENOENT"), Redmi K20 Pro (raphael: "current build and device state unconfirmed") and OnePlus 7 Pro (guacamole: iOS 16.7.16 userland reached, GPU blocked). The guacamole record is telling: UniXNU's own SM8150 pattern is the ios-sweet 16K kernel plus UniXNU's boot chain and Project Aloha UEFI, not its 4K kernel ([guacamole.md](https://github.com/UniXNU/UniXNU/blob/main/docs/devices/guacamole.md)). There is no vayu, davinci, Pixel 4 or Poco record, no SM8150 SoC-common repo in the docs, and no Adreno 640 component; the GPU guide says another generation needs its own kernel backend and compiler support ([porting/gpu.md](https://github.com/UniXNU/UniXNU/blob/main/docs/porting/gpu.md), [components.toml](https://github.com/UniXNU/UniXNU/blob/main/components.toml)). I found no effort estimate anywhere in the porting docs.

Outside UniXNU, the other Xiaomi-family claims form a ladder of evidence. HackiOS (also spelled HakiOS) targets the Poco X5 Pro (redwood, Snapdragon 778G) with xnu-8796 and later xnu-12377, a custom loader and `fastboot boot` ([Hakky Handbook summary](https://book.st-hakky.com/en/news/run-ios-16-5-firmware-on-android), [GitHub README](https://github.com/oosexgang/hackios-xnu-kernel)). hackios.net lists lock/home screen, touch, GPU, Wi-Fi, sound and camera as working and Bluetooth as not, citing an unnamed independent reproduction ([hackios.net](https://hackios.net)). ios-topaz (Redmi Note 12 4G, Snapdragon 685) reportedly reached SpringBoard in about three minutes with four cores disabled for lack of 16K support, but that is press-only ([Gizchina](https://www.gizchina.com/redmi-phones/real-ios-16-now-boots-on-a-redmi-note-12-4g-and-tinkerers-can-try-it)). ios-sweet (Redmi Note 10 Pro, SM7150) and a Redmi K90 Pro Max iOS 17 demo round out the list, the latter press-only with no SoC stated ([XimiTime](https://ximitime.com/ios-17-successfully-ported-to-redmi-k90-pro-max-101538/)). None is a daily-driver, and every repo labels itself experimental. Nothing earlier counts as precedent: Corellium's Project Sandcastle ran Android on iPhones, the opposite direction ([projectsandcastle.org/history](https://projectsandcastle.org/history)), and QEMU iOS work emulates Apple silicon rather than booting real non-Apple SoCs ([Aleph Security](https://alephsecurity.com/2019/06/17/xnu-qemu-arm64-1/)).

## Nearly all evidence is self-published, and the notes disagree in several places

The project is a GitHub organization created 2026-10-19 whose main repo has about 3.1k stars and about 1,065 commits in roughly 30 days, starting from a one-shot "Initial import" ([GitHub API org](https://api.github.com/orgs/UniXNU), [contributors API](https://api.github.com/repos/UniXNU/UniXNU/contributors)). No real names or legal entity appear, an `AGENTS.md` sits at the repo root, and a "UniXNU Docs" identity authored about 297 commits that mirror human ones, so AI-assisted workflow is likely (inference). The press coverage is thin: the PBX Science article itself says the "first third-party ARM project to create and open-source a Metal GPU driver" claim comes from the authors and is unconfirmed ([PBX Science](https://pbxscience.com/ipados-boots-on-a-xiaomi-tablet-with-a-native-metal-gpu-driver-what-unixnu-has-actually-proven/)). I found no Hacker News, Reddit, Phoronix or XDA coverage of UniXNU specifically (one search; absence is weak evidence). The repo's own format helps: milestone records carry commands, revisions and boot IDs, and distinguish `implemented` from `device-verified`. That makes the claims checkable in principle, but nobody outside the projects has checked them.

## Vayu shares its silicon with a working precedent, so 16K pages and the Pixel 4 recipe apply

Vayu is the same SM8150 family as the Pixel 4 and Xiaomi's cepheus, raphael and nabu, so the CPU/interconnect work in ios-flame should transfer. The strongest evidence on page size comes from the later note. QEMU's Cortex-A55 and Cortex-A76 models both report `ID_AA64MMFR0_EL1 = 0x101122`, which decodes to 16K, 4K and 64K granules all supported; ios-sweet read the same value on real Kryo 470 hardware ("16K granule YES, 4K YES") and verified a 16K MMU; ios-flame runs all eight SM8150 cores (4x A55 + 4x A76) at full clock on the stock-16K "SWEET" config ([QEMU cpu64.c](https://github.com/qemu/qemu/blob/master/target/arm/tcg/cpu64.c), [ios-sweet NOTES](https://github.com/NWylynko/ios-flame/blob/main/docs/ios-sweet/NOTES.md), [ios-flame README](https://github.com/NWylynko/ios-flame)). The 4K problem shows up only on Cortex-A53-class start-up cores: ios-topaz found its bootloader launched on a Silver core with `TGran16 = 0` and had to hop to a Gold core ([ios-topaz shim.c](https://github.com/MakrSas/ios-topaz/blob/main/shim/shim.c)). My conclusion is that vayu does not need UniXNU's 4K patches for the CPU, and its own SM8150 record (guacamole) takes the 16K route. Two caveats remain: nobody has published the vayu register, and a boot-core check is needed because HakiOS's vayu config boots on `bootcpu=7` (a prime A76) ([ios-vayu README](https://github.com/telegdyd/ios-vayu/blob/vayu-dev/devices/poco-x3-pro/README.md)). Whether ABL or UEFI hands over at EL1 or EL2 on vayu is also not established; ios-flame uses PSCI over `smc`, consistent with EL1 under a hypervisor, and I treat EL1 as the working assumption.

On the ios-flame route, the SoC-generic parts reportedly work: GIC-600, 19.2 MHz timer, PSCI 1.1, PM8150, RPMh votes, DWC3 USB with Ethernet and SSH, UFSHCI 3.0, an Adreno 640 kernel driver with a Turnip Vulkan path, and WCN3990 Wi-Fi. The status on the Pixel 4 (2026-10-22, kernel 0124) is Settings, Safari and Notes running, about 20-26 fps swiping, ad hoc-signed IPAs launching, and "not a usable phone OS"; audio, Bluetooth, cellular, camera, sensors and video decode do not work, and security is mostly disabled with a stub keystore ([ios-flame README](https://github.com/NWylynko/ios-flame), [NOTES.md](https://github.com/NWylynko/ios-flame/blob/main/NOTES.md)). The Pixel-4-specific parts are the ones that must be rewritten for vayu: the display (vayu is a 1080x2400, 120 Hz, 4-lane DSC 1.1 video-mode LCD with a PM8150L WLED backlight, not Pixel 4's command-mode OLED), touch (Novatek on SPI instead of ST FTS), GPIOs, Xiaomi ABL boot-image rules, partition layout and board firmware ([vayu-sm8150.dtsi](https://raw.githubusercontent.com/MiCode/Xiaomi_Kernel_OpenSource/vayu-r-oss/arch/arm64/boot/dts/qcom/vayu-sm8150.dtsi), [dsi panel dtsi](https://raw.githubusercontent.com/MiCode/Xiaomi_Kernel_OpenSource/vayu-r-oss/arch/arm64/boot/dts/qcom/dsi-panel-j20s-36-02-0a-lcd-dsc-vid.dtsi)). The cepheus fork shows the pattern in practice ("most low-level bring-up code copies directly from ios-flame") ([ios-cepheus](https://github.com/Mattia990/ios-cepheus)).

Four public repos already target vayu, and none is independently confirmed. `telegdyd/ios-vayu` (branch `vayu-dev`, created 2026-11-06, 0 stars) is a HakiOS fork whose device README reports SpringBoard drawn on an Adreno 640 via Mesa/freedreno, Novatek touch, cpufreq, battery and buttons, sound with crackle, camera frames, LTE registration without data, and a 2.4 GHz WPA2 Wi-Fi join, while stating that the tree "has not been booted since" being rebuilt on upstream and that it needs a custom GPT partition for the iOS volume ([ios-vayu README](https://github.com/telegdyd/ios-vayu/blob/vayu-dev/devices/poco-x3-pro/README.md)). `PowerPointKotik/ios-vayu` is an ios-sweet fork with a bring-up log (vayu ADT, UFS read-only, touch probe), no home-screen claim, and a 3 GiB DRAM window, which is smaller than your 8 GB ([VAYU.md](https://github.com/PowerPointKotik/ios-vayu/blob/main/VAYU.md)). `Redactedslair/ios-vayu` is an unchanged ios-flame tree, and `pruefsumme/vayu-UniXNU` was created on 2026-11-24 and is empty ([repo](https://github.com/pruefsumme/vayu-UniXNU)). On the UEFI side, Mu-Silicium and woa-msmnile have a vayu target: display, UFS and buttons work, Linux and Windows boot, USB host and USB-PD do not, and Mu-Silicium marks it "Inactive" ([Status.md](https://raw.githubusercontent.com/Project-Silicium/Mu-Silicium/main/Status.md), [msmnilePkg](https://github.com/woa-msmnile/msmnilePkg)).

Achievable level on vayu, by tier. A first tier (boot from RAM to launchd or SpringBoard, touch, UFS root, USB Ethernet/SSH) is reported on the identical SoC and by a vayu fork, so I expect it to be reachable. A second tier (GPU compositing via Turnip at Pixel-4-like ~20-26 fps, Wi-Fi) is plausible but depends on firmware extraction and on the WCN3990/3998 question. Everything else is out of reach or unproven: cellular (a Qualcomm modem has no Apple baseband stack; HakiOS marks it "partly", hackiosx says no project handles it ([hackiosx future](https://hackiosx.dev/future.html))), Bluetooth, camera, sensors, suspend, battery readout, hardware video decode, and App Store/Apple ID/iCloud (no SEP or FairPlay). The OS version ceiling is set by PAC: iPhone images stop at iOS 16.7.16 (iPhone X, A11), and plain-arm64 iPad images (iPadOS 17.7.x, and 18.7.x in one raphael record) are the only newer options, via UniXNU profiles that nobody has shown on SM8150 hardware ([hackiosx compatibility](https://hackiosx.dev/compatibility.html), [devices.toml](https://github.com/UniXNU/UniXNU/blob/main/devices.toml)). Effort figures are precedent only: ios-sweet went from first attempt to home screen in about four days, and ios-flame from unlock to Metal-rendered SpringBoard in about three, but much of that was likely AI-assisted and iterative, so treat them as evidence that a fork is far cheaper than a first port, not as a schedule.

## What to do next on this phone, in order

The ordering puts the slowest, irreversible step first and defers every write to the phone until backups exist.

1. Start the unlock clock now, because it is the long pole. Use a global (non-China) Xiaomi account that is at least 30 days old and request approval through the Xiaomi Community app (approval slots open daily at 12:00 China time, UTC+8; the daily quota size is not published) ([Notebookcheck](https://www.notebookcheck.net/Unlocking-bootloader-Xiaomi-does-it-better-than-Samsung-despite-some-caveats.1228387.0.html)). The OEM-unlock toggle you can already flip is only one half of this; Xiaomi's per-account approval is the real gate. Sources conflict on the wait (72 hours, 3-7 days, 5-7 days, "over 7 days") and on per-account limits (1 versus 3 devices), so budget more than 7 days and check which account you apply with, since a second device needs a separate account and phone number. Unlocking wipes the phone and cannot be done and then reversed without a wipe cycle, so nothing else below should wait on it except steps that need an unlocked bootloader.
2. While waiting, back up everything the wipe will destroy and everything the port will need. Back up user data off the phone now. Collect the files the ports extract from the phone's own Android: GPU firmware (`a640_gmu`, `a640_zap`, `a630_sqe`), Wi-Fi blobs (`wlanmdsp.mbn`, board data) and modem partitions, which ios-flame pulled from vendor firmware plus the user's own modemst1/modemst2/fsg/fsc backups ([ios-flame README](https://github.com/NWylynko/ios-flame)). Identify your panel variant (the 0x36 Tianma or 0x42 CSOT family) from the stock firmware's panel and touch-firmware selection, and read the Wi-Fi chip identity from the stock `wlan` firmware, which settles WCN3990 versus 3998 without guessing. None of the notes confirm how to read these on-device; this is an inference from the DT structure.
3. Pick the route: start from the ios-flame lineage (preferably the `ios-cepheus` fork, which is the closest SM8150 Xiaomi example, or `PowerPointKotik/ios-vayu`, which already has a vayu ADT and touch probe), and use `telegdyd/ios-vayu` as a reference for vayu-specific facts rather than as a base to trust. Reasons: flame/cepheus use stock 16K XNU, `fastboot boot` into RAM, and write the root only to `userdata` (no repartitioning, nothing in the boot chain flashed), whereas `telegdyd/ios-vayu` needs a custom GPT partition and is explicitly unbooted since a rebuild. UniXNU is not the starting point: it has no vayu or SM8150 SoC repo and no Adreno 640 driver. Borrow from it selectively (DarwinBoot, the NativeAdreno ABI headers and Turnip Darwin patches that ios-flame already reuses), and treat `pruefsumme/vayu-UniXNU` as an empty placeholder. Do this step on a PC and in QEMU first; none of it needs the phone.
4. Before the first `fastboot boot`, check the specifics that differ from the Pixel 4: read the boot CPU's MIDR (ios-topaz shows ABL may not start on the core you expect), and confirm Xiaomi's ABL accepts your image format. Vayu's AOSP-side config uses boot header v2 with AVB and a dynamic `super` partition ([BoardConfigCommon.mk](https://raw.githubusercontent.com/xiaomi-sm8150-devs/android_device_xiaomi_sm8150-common/lineage-20/BoardConfigCommon.mk)), but the sources do not say that `fastboot boot` works on Xiaomi's unlocked ABL. ios-topaz had to adapt to a Xiaomi ABL that dropped older boot-image formats, and ios-flame needed LZ4-compressed kernels and an AVB footer on Google's ABL. Expect a trial-and-error phase here and change one variable at a time.
5. After unlock, take a full partition-table and critical-partition backup before any write. The one concrete vayu brick report in the notes (Xiaomi EU forum, 7 Oct 2026) is an owner who deleted partitions from Windows and now reaches only EDL 9008; QFIL with official firmware did not recover it, and a reply says an authorized Xiaomi EDL account is often required ([Xiaomi EU thread](https://www.xiaomi.eu/community/threads/poco-x3-pro-vayu-stuck-in-edl.76788/)). The stock firehose is auth-locked and "patched" firehose files come from untrustworthy sites, so assume a hard brick is not recoverable by you. Stay on RAM-booted images, never touch xbl or abl, and avoid the GPT-modifying path in `telegdyd/ios-vayu` unless you have a verified backup. Write the iOS root image to `userdata` the way ios-flame did (from recovery with `dd`, because "ABL hangs on the last chunk" of `fastboot flash`). Note that I found no vayu anti-rollback index or policy for MIUI 14, so do not flash older firmware.
6. Bring-up order on the phone: UART-free first signs (display via the ABL-initialized framebuffer, volume keys), then UFS root, then touch, then USB networking so you can SSH in, then the GPU, then Wi-Fi. Use the Mu-Silicium vayu UEFI only if you pursue the UEFI route; it is marked "Inactive", the release page was empty, and USB host does not work in it, so expect to build it yourself.
7. Set your expectation before you invest: the target is a lab prototype, not a phone replacement. Keep Android recoverable (you can still `fastboot flash` stock via an unlocked bootloader), and plan to relock only if you accept a wipe cycle (relock behaviour on vayu is not covered in the notes).

On legal and licensing, the picture is permissive on code and silent on Apple's terms. UniXNU's code is BSD-2-Clause-Patent per its README (GitHub reports "Other"); HakiOS is MIT plus APSL 2.0 for XNU extensions; ios-sweet is MIT ([README](https://github.com/UniXNU/UniXNU/blob/main/README.md), [HakiOS README](https://github.com/burdenghost/Hackios), [ios-sweet README](https://github.com/dipa-studio/ios-sweet)). XNU sources come from Apple's public drops, and every project has you supply the IPSW, kernelcache and trust cache yourself; UniXNU's CONTRIBUTING forbids committing Apple IPSWs, kernelcaches, disk images or vendor firmware, and its CI notes tell users to run builds in a fork and delete the run after downloading ([CONTRIBUTING.md](https://github.com/UniXNU/UniXNU/blob/main/CONTRIBUTING.md), [sheng.md](https://github.com/UniXNU/UniXNU/blob/main/docs/devices/sheng.md)). The Apple IPSW and OS license terms are not discussed in any project doc I read, and I found no Apple response or DMCA action. So the practical rules are: build locally for private research, never redistribute the resulting image or the vendor firmware blobs, and do not treat any of this as legal advice. The Apple-ID, App Store and activation features are out of scope for every project, which also keeps you away from Apple's services.

## Conclusion

The framing that this is "UniXNU on vayu" turns out to be the wrong unit of analysis. UniXNU's contribution is the boot chain and the 4K-page work, and neither is needed on a Kryo 485 phone whose A76/A55 cores accept 16K pages. The usable path is the ios-sweet and ios-flame lineage, which already treats SM8150 as a solved SoC and leaves only vayu's board-specific pieces (a 120 Hz DSC LCD in two panel variants, Novatek SPI touch, Xiaomi's ABL, an unconfirmed Wi-Fi chip) as new work. The work that remains is mostly board code, firmware extraction and bootloader trial and error.

What would change this assessment is evidence the notes lack: a measured `ID_AA64MMFR0_EL1` dump from vayu, any third-party video or log of the `telegdyd/ios-vayu` claims, and an authoritative statement of Xiaomi's current unlock wait. Until then the whole stack is a month-old, self-reported, partly AI-assisted ecosystem, and the right bet is a low-risk, reversible experiment: unlock early, back up everything, boot only from RAM, and write only to `userdata`.
